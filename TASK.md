# Тестовое задание: Python backend-разработчик

Здравствуйте! Спасибо, что откликнулись.

Задание похоже на нашу обычную работу. Сервисы с нуля мы пишем редко. Гораздо чаще разбираемся в существующем коде, чиним баги по жалобам поддержки и добавляем функциональность так, чтобы она вписалась в архитектуру проекта.

Ориентир по времени — около 8 часов. Срок — 4 календарных дня. Если нужно больше времени, напишите.

## 1. Что это за сервис

`credits-service` — упрощённая версия биллинга AI-генераций в наших мобильных приложениях:

1. Пользователь покупает пакет кредитов. Платёжная система присылает вебхук `POST /webhooks/purchase`, сервис начисляет кредиты.
2. Пользователь запускает генерацию (`POST /generations`). Сервис списывает стоимость и ставит задачу в очередь RabbitMQ.
3. Воркер забирает задачу, вызывает внешний AI-провайдер и сохраняет результат.
4. Клиент опрашивает статус (`GET /generations/{id}`) и смотрит баланс (`GET /users/{user_id}/balance`).

Стек: Python 3.12, FastAPI, async SQLAlchemy 2 + MySQL 8, Alembic, Redis (кэш баланса), RabbitMQ через FastStream, pytest, uv, Docker Compose.

Запуск, устройство слоёв и контракт API описаны в [README.md](README.md).

Внешний провайдер заменён имитацией `FakeGenerationProvider`, этот класс менять нельзя. Поведение имитации задаётся маркером в тексте prompt:

- `[fail]` — провайдер окончательно отказывает (`ProviderPermanentError`);
- `[flaky:N]` — первые N вызовов с этим prompt падают с `ProviderTemporaryError`, счётчик хранится в памяти процесса воркера;
- `[slow]` — провайдер зависает на 5 минут;
- без маркера — успешный ответ за 0.1–0.5 секунды.

## 2. Задание

### Часть 1. Баги из поддержки

Поддержка прислала четыре жалобы. Ниже описаны только симптомы. Найдите причину каждой и исправьте.

1. **«Купил кредиты, а баланс не изменился».** После успешной покупки `GET /users/{user_id}/balance` ещё несколько минут показывает старое значение, потом «само проходит».
2. **«Одна покупка начислилась дважды».** Платёжная система повторяет вебхук, если не получила ответ вовремя, и иногда повторы приходят почти одновременно. У части пользователей кредиты за одну покупку начислены два раза.
3. **«Запустил две генерации, заплатил за одну».** Пользователь с балансом ровно на одну генерацию быстро нажал кнопку дважды. Обе генерации приняты (`202`), списание прошло один раз.
4. **«Генерация висит в pending навсегда».** Часть генераций никогда не выходит из статуса `pending`. В логах воркера в это время встречается `Generation not found`.

### Часть 2. Сбои провайдера и возврат кредитов

Сейчас любая ошибка провайдера оставляет генерацию в статусе `processing`, кредиты пользователю не возвращаются. Нужно это исправить.

Требования:

- При `ProviderTemporaryError` и при превышении таймаута вызов повторяется, паузы между попытками растут.
- Таймаут действует на каждую попытку отдельно. Превышение таймаута считается временной ошибкой.
- При `ProviderPermanentError` генерация сразу переходит в `failed`, без повторов.
- Когда попытки закончились, генерация переходит в `failed`.
- У генерации в `failed` поле `error` содержит понятный текст ошибки.
- При переходе в `failed` пользователю возвращается стоимость генерации. В истории операций появляется запись с `kind = generation_refund`, `amount` равен стоимости генерации (положительное число), `reference_id` равен id генерации.
- Кредиты за одну генерацию не должны вернуться дважды. В том числе когда RabbitMQ доставляет одно сообщение повторно.
- Настройки задаются через переменные окружения и прописаны в `docker-compose.yml` и `.env.example`:
  - `PROVIDER_MAX_ATTEMPTS` — общее число попыток, включая первую, по умолчанию `3`;
  - `PROVIDER_TIMEOUT_SECONDS` — таймаут одной попытки, по умолчанию `5`;
  - базовая пауза между попытками, имя и значение по умолчанию на ваше усмотрение.
- С настройками по умолчанию одиночная генерация при свободном воркере приходит в `completed` или `failed` не позже чем через 60 секунд после создания.

Где делать повторы — циклом внутри обработчика, повторной публикацией в очередь или иначе — решайте сами и объясните выбор в `SOLUTION.md`.

Доводить до финального статуса генерации, которые зависли в `processing` из-за падения воркера, не обязательно, см. раздел 4. Что делать с генерациями, которые уже висят в проде в `pending`, решите сами и опишите в `SOLUTION.md`.

### Часть 3. Тесты

Напишите тесты на исправленные баги и на новую логику. Юнит-тесты на in-memory подменах лежат в `tests/`, их можно расширять.

Если какой-то сценарий трудно проверить юнит-тестом (например, конкурентный), достаточно описать в `SOLUTION.md`, как вы его проверяли.

### Часть 4. `SOLUTION.md`

Положите в корень репозитория `SOLUTION.md`. Коротко:

1. По каждому багу: причина в одном-двух предложениях, как исправили и почему так.
2. Как устроена обработка сбоев провайдера и что гарантирует, что кредиты не вернутся дважды.
3. Что осталось неидеальным и что вы сделали бы при большем времени.
4. Ответы на два вопроса, по 3–6 предложений:
   - Что произойдёт, если воркер упадёт после успешного ответа провайдера, но до сохранения результата в БД? Что увидит пользователь и как бы вы это закрыли?
   - Что сломается или станет узким местом, если запустить 10 реплик воркера и 5 реплик API?
5. Если пользовались ИИ-инструментами (Cursor, Copilot, ChatGPT и т.п.), напишите, для чего.

## 3. Ограничения

- Контракт HTTP API из README не меняется: пути, поля и коды ответов остаются прежними. Добавлять новые поля можно.
- Решение соблюдает слои и направление зависимостей из README. Бизнес-логика живёт в `application`, SQLAlchemy — только в `infrastructure`.
- Схема БД меняется только новыми ревизиями Alembic, `0001_initial` не трогаем. Сервис уже работает в проде, в таблицах лежат реальные данные, в том числе последствия описанных багов. Миграции должны применяться к такой базе.
- `FakeGenerationProvider` не меняется.
- Проект поднимается командой `docker compose up --build`, тесты проходят через `uv run pytest`.

## 4. Будет плюсом

- Фоновая сверка генераций, зависших в `processing` дольше N минут: перевод в `failed` с возвратом кредитов.
- Логи, по которым дежурный сможет разобраться в инциденте.
- Интеграционные тесты на реальной MySQL, включая конкурентные сценарии.

Если что-то не успеваете, напишите об этом в `SOLUTION.md`. Это лучше, чем сделать наспех.

## 6. Про ИИ-инструменты

Пользоваться ими можно, мы сами работаем в Cursor. Просим указать в `SOLUTION.md`, где и для чего вы их использовали.

После сдачи будет встреча на 45–60 минут. Вы покажете решение, мы обсудим его, а потом вместе внесём в код небольшое изменение.
